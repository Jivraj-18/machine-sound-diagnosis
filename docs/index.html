Can an existing model hear which fault a compressor has?

An exploratory baseline on 1,800 one-second recordings of one air compressor in 8 states (healthy + 7 faults).

Yes, on this dataset, when you show it a few examples. With 5 labelled clips per fault, the best existing model (FISHER, a model pre-trained on industrial sounds) names the right fault % of the time, and % with 10 clips. Simple hand-built sound features are close behind at %.

Without examples it does not work: naming the fault "zero-shot" scored % (Gemini 3.1 Pro) and % (CLAP), against 12.5% for a random guess.

Demo-worthy as "teach it a few examples of each fault", not as "AI that recognises faults by itself", and only after a test on a second machine, because every clip here comes from one compressor in one lab.

2 · The setup in one glance

One compressor, eight states, 1-second clips

The data is the public IIT Kanpur air-compressor dataset: a single-stage reciprocating compressor recorded with one microphone in one lab, 225 clips per state, each 1 second long. Seven faults were deliberately introduced one at a time.

Models compared

  • Handcrafted features: classic signal processing (band energies, MFCCs, spectral statistics). No neural network.
  • General audio models (pre-trained on everyday sounds, used frozen): BEATs, Dasheng, CLAP.
  • Industrial-signal models (pre-trained on machine sounds and vibration): FISHER, ECHO.
  • Zero-shot (no examples at all): CLAP matched against a text description of each fault, and Gemini 3.1 Pro, an audio-capable large language model, which hears the clip with the list of 8 states and picks one.

"Frozen" means no model was re-trained. Each model turns a clip into a numeric fingerprint, and a small standard classifier (logistic regression or SVM) learns the faults from the labelled examples.

    6 · Can it identify useful problems on its own?

    Naming the fault without examples

    No. Without examples, both approaches are at chance: % (Gemini) and % (CLAP) vs 12.5% for guessing.

    Telling which fault it is works well, but only after the model has been shown labelled examples of each fault (section 4). The question here is whether a model can name a fault it has never been shown. Two attempts:

    • CLAP compares the sound against a text description of each state ("an air compressor with a leaking inlet valve", …).
    • Gemini 3.1 Pro heard each clip together with the list of 8 states and a one-line description of each, and had to pick one. The prompt was identical for every clip. Its written reasons sound plausible ("rhythmic metallic tapping…"), but they don't match the actual fault. That's the risky failure for a demo: a confident, articulate, wrong answer.

    7 · Caveats

    Why "~100%" is less impressive than it sounds

    1. One compressor, one lab, one microphone. Every result is "telling apart recordings from the same machine". Nothing here shows that a model trained on this data works on another compressor, room or microphone. That is the claim a customer would care about, and it is untested.
    2. Near-100% is expected on this dataset. The original paper reports ~99.8% with classic features; our hand-built features also reach 100% under 5-fold CV. Because the task is this easy, the dataset can only show what pre-trained models add when labels are scarce (1–3 examples per fault).
    3. Each fault was probably recorded in its own session. The label is therefore tangled up with everything else about that session (background noise, microphone placement, tank pressure). The block split rules out drift within a session, but this data can't separate "the fault" from "the day it was recorded".
    4. Sample rate. The files don't state it. We concluded 50 kHz (each file = 1 s): the original recordings are documented at 50 kHz, and the compressor's piston rhythm then works out to ~440 rpm, a normal speed (16 kHz would imply an implausible ~140 rpm). We ran every pre-trained model under both 50 kHz and 16 kHz. The conclusions didn't change, only the ranking: the general audio models score a few points higher when the clip is read as 16 kHz (played slower), while FISHER is best at 50 kHz. Use the toggle in section 4 to compare.
    5. A recording artefact. of the 1,800 files contain a click at exactly the same sample (the midpoint), where two segments seem to have been joined (none in Healthy). It makes those clips slightly harder to classify, not easier, so it doesn't inflate the scores.
    6. What failed or was skipped. FISHER initially failed to load with the current version of the transformers library. It ran after pinning an older version, with no change to the model. EAT was not run (the brief allowed either Dasheng or EAT; Dasheng was used). I compared the misclassified clips by their spectra rather than by ear.

    8 · What a demo would need

    Promising, with one test to run first

    • Frame it as "enrolment": record a handful of examples of each known fault on the customer's machine, then the system recognises them from then on. Healthy vs faulty is rock-solid; "which valve" is the weakest part.
    • Before any claim to a customer, test transfer: record a second compressor (or the same one on another day, with the microphone moved). Train on this data plus a few clips from the new setting, then test on the rest. If accuracy holds, there is a product story. If it collapses, the ~100% here only meant "this machine, this session".
    • Use real fault data: a client's own maintenance logs, matched to recordings, would show whether real-world faults are as separable as seeded lab faults.
    • Don't build on zero-shot (section 6), and don't let an LLM explain diagnoses it can't make.
    • Compute is not the obstacle. The models are small and run in real time on a laptop. At fleet scale, measured costs are cents per machine per month on CPU:

    9 · Method & reproducibility

    How to re-run it

    All code, results and the full technical write-up are in the repository: github.com/Jivraj-18/machine-sound-diagnosis (REPORT.md).

    python features_handcrafted.py --sr 50000        # handcrafted features (CPU)
python embed_pretrained.py --raw cache/raw.npz    # pre-trained embeddings (GPU; ran on a Kaggle T4)
python zeroshot_clap.py
python zeroshot_gemini.py --sr 50k                # needs a Gemini API key
python evaluate.py                                # results.csv, confusion matrices, misclassified clips
python analyze_misses.py && python cost_estimate.py && python build_site.py
    • Protocols: 5-fold stratified CV; few-shot with k = 1, 3, 5, 10 clips per class (kNN and logistic regression, 10 random draws, the same draws for every model); block split by recording number; zero-shot on a fixed subset of 20 clips per class. Metric: macro (class-balanced) accuracy.
    • Versions: analysis on Python 3.11 with scikit-learn 1.9.1, librosa 0.11.0, numpy 2.2.6; embeddings on torch 2.11.0 and transformers 5.16.1 (FISHER: transformers 4.57.1). Full pins are in requirements.txt and requirements-gpu.txt.
    • Model checkpoints: BEATs iter3+ AS2M, Dasheng-base, CLAP laion/larger_clap_general, ECHO-small (yucongzh/echo-small-0824), FISHER-small (jiangab/FISHER-small-0723), Gemini gemini-3.1-pro-preview.
    • Audio on this page is resampled from 50 kHz to 48 kHz for browser playback; nothing audible is lost (the recordings contain nothing above ~15 kHz).

    Dataset: N. K. Verma, R. K. Sevakula, S. Dixit and A. Salour, "Intelligent Condition Based Monitoring Using Acoustic Signals for Air Compressors", IEEE Transactions on Reliability, 65(1), 2016. Data from the IIT Kanpur Intelligent Instrumentation Lab datasets page. This page hosts only the short clips it plays; the dataset itself is not redistributed.

    Models: BEATs (Microsoft), Dasheng, CLAP (LAION), ECHO, FISHER, Gemini (Google). Exploratory research results, October 2026.
